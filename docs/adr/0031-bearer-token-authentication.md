# ADR 0031: Bearer-token authentication for the HTTP and WebSocket front doors

Status: accepted

Requirements P3-01 and P3-02 (the transport that carries them needs an identity). Issue [#521](https://github.com/moncifem/latticedb/issues/521), design
[live collaboration](../design/live-collaboration.md), threat-model gaps G-03 and G-05.

Acceptance: the owner approved bearer tokens in chat on 2026-10-30 on these terms: tokens are generated by
the server with at least 256 bits of entropy, stored only as a salted hash, revocation closes live
connections, and rotation allows a bounded overlap of two tokens. Per-table grants for a token's account are
a separate decision ([#522](https://github.com/moncifem/latticedb/issues/522)). This ADR is about
authentication only. The acceptance covers the decision, not a release, a phase gate, or the gateway
itself, which does not exist yet ([#524](https://github.com/moncifem/latticedb/issues/524)). An independent
review of the final diff is recorded in the pull request.

## Context

SCRAM-SHA-256 is a PostgreSQL wire exchange. A WebSocket upgrade and an MCP or HTTP call are single HTTP
requests, and the clients that make them (agents, SDKs, a local stdio proxy) can carry one header value
but cannot run a multi-message challenge. The gateway still has to answer one question before it builds a
`Principal` (ADR 0026): which account is this connection? When this was written, no transport answered it; the loopback
development principal is the only identity an HTTP request could get, which is why the design requires it
to be refused over HTTP unless a token is present.

## Decision

### The token

A token is a bearer secret in one string, `lat_<id>_<secret>`, always 64 bytes:

| Part | Form | Meaning |
|---|---|---|
| `lat_` | literal | Lets secret scanners and humans recognise a Lattice token |
| `<id>` | 16 lowercase hex digits (8 bytes) | Non-secret lookup key. It is looked up in the credential file, so a request touches one entry |
| `_` | literal | Separator. Both parts have fixed width, so it is never ambiguous |
| `<secret>` | 43 characters of unpadded base64url (32 bytes) | The secret. 256 bits from the operating system random source |

The server generates tokens (`lattice_api::bearer::issue`, fed by `lattice_seams::OsRng` outside tests:
seven 64-bit draws become the id, a 16-byte salt and the secret). There is no function that imports a
token a person chose, and the verifier accepts exactly this shape: any other length, case, separator or
non-canonical base64 (set padding bits) is refused before any lookup. A secret shorter than 32 bytes, such
as a word, therefore cannot be configured at all.

### What is stored

Only a salted verifier: `SHA-256("lattice-bearer-token-v1" 0x00 || salt || id || secret)` with a fresh
16-byte salt per token. The secret has 256 bits of entropy, so a fast hash is enough: no guess list
exists to slow down, and a slow function (PBKDF2, Argon2) would only let anyone who can send requests spend
the server's CPU. The salt keeps equal secrets and equal files from sharing verifiers; the id is hashed in
so a verifier cannot be moved to another id. SHA-256 comes from `sha2`, already in the tree for SCRAM; no
new cryptographic dependency is added.

The secret is shown once, by the program that issues it, and is never stored: the credential file cannot
reproduce it. A lost token is revoked and replaced.

### The credential file

A text file, strict and canonical, so that what is parsed is what would be written back:

```
lattice-bearer-tokens v1
<id> TAB <account> TAB active|revoked TAB <created> TAB <expires>|- TAB <salt hex> TAB <verifier hex>
```

- Times are Unix seconds, canonical decimal (no sign, no leading zero). `-` means no expiry. An expiry must
  be after the creation time.
- Every line, including the last, ends in `\n`: a truncated file is refused. No blank lines, comments,
  carriage returns, extra fields, upper-case hex or repeated ids.
- Bounds, checked before parsing: 256 KiB, 1,024 entries (revoked ones included; they are removed only by `lattice account token prune` (#582); the longest possible
  1,024 lines are about 220 KiB). A revoked entry stays so its id is never reissued and so a stolen,
  revoked token can be recognised in the log.
- Version: the header line. A format change is `v2`, refused by `v1` readers. This is operator
  configuration beside the data directory, not a data or wire format; it needs no RFC, but any change to
  the line grammar needs a new ADR.
- Rotation rules are part of the grammar: at most two `active` entries per account, and when there are two
  the older one must expire no later than seven days after the newer one was created. The program that
  rotates sets that expiry. A third active token, or an overlap with no end, is a refused file. An expired token still counts toward the two-active limit until it is revoked. Equal creation seconds are ordered by id.

Location and handling. The host will name the file on its command line (`--gateway-tokens FILE`, which the
gateway of #524 added beside `--scram-verifiers`) and the file lives outside the data directory, so a copy or backup of the data does not carry
credentials. On Unix it must be a regular file with mode 0600 (0400 is accepted) in a directory that group
and others cannot write to (create with 0700); `latticed::load_credential_store` refuses anything broader, and the gateway calls it at start and at every
reload. Only mode bits are checked: file ownership is not. Writers replace the file atomically: a 0600
temporary file in the same directory is written, `fsync`ed, renamed over the target, and the directory is
`fsync`ed (`latticed::write_credential_store`). Temporary names are unique per write and the writer removes only a file it created; it applies the same directory check as the loader, and the loader opens with `O_NONBLOCK | O_NOFOLLOW` so a FIFO or symlink at the path is refused. Writers are serialized by the caller; this ADR does not
define a lock. On Windows both load and write refuse until an owner-only ACL check exists
([#577](https://github.com/moncifem/latticedb/issues/577)): failing closed is better than reading an
unchecked credential file.

### Token to principal

A token entry names an account. The account name follows the same rule as SCRAM accounts (1 to 63 bytes,
no control characters; `auth::valid_account_name` is the single check for both). The verifier returns
`Principal::account(<name>)`, the same kind and the same name a SCRAM login of that account gets, so one
account is one principal in every transport, and grants (ADR 0026, [#522](https://github.com/moncifem/latticedb/issues/522))
and the row author ([#520](https://github.com/moncifem/latticedb/issues/520)) are keyed by one name. An
account may have tokens only, a SCRAM verifier only, or both. How the credential was proven is not part of
the identity. A token never carries scopes: what an account may do is decided by the account's grants.

### Verification

`verify_bearer(header, store, now)` takes the value of one `Authorization` header, the parsed store and the
time, and is pure. It requires `Bearer ` (the scheme is case-insensitive, RFC 7235) followed by a token of
the exact shape, at most 128 bytes in all.

- Unknown id and wrong secret run the same hash and the same constant-time comparison over the 32 verifier
  bytes (`subtle`), the unknown case against fixed decoy values, and return the same value and text:
  `invalid bearer credentials` (one `Display` text for every `AuthError`, a missing header included). Shape errors return earlier, because the shape is public.
- A revoked or expired token is told apart (`RejectReason::Revoked`, `Expired`) only after its secret
  verified, so the distinction is available to someone who holds the token and to nobody else. The client
  still gets the single 401 answer; the distinction is for the host's own event log.
- An entry is expired at its expiry second, not after it.
- Claim limits: the comparison is constant time; lookup by the public id is a bounded search over at most
  1,024 entries; no end-to-end timing guarantee is claimed or measured. The planted bug
  `TokenAcceptsPrefix` (the hash sees only a prefix of the secret) is caught by the prefix witness; a
  timing difference cannot be tested portably, so it is not planted.

### Failed attempts

The verifier does not log and does not count. It returns `AuthError`, which the host feeds to a
`FailureLimiter` keyed by client address (IPv6 by /64, IPv4-mapped as IPv4, like the handshake limiter):
10 failures per address in 60 seconds, after which the host refuses further attempts from that address
with 429 without verifying until the window passes. A success clears the address, so the failure budget resets on success. The table holds at most
1,024 addresses and fails open when full of live failures: an attacker who fills it gains uncounted
guesses against a 256-bit secret, while failing closed would let that attacker lock real clients out. The
limiter is a resource and log-noise bound, not what protects a token. The host builds the security event
([#530](https://github.com/moncifem/latticedb/issues/530)) from the error kind, the address and the time,
never from the header.

### Expiry, revocation, rotation, reload

Decided here, implemented and tested in [#577](https://github.com/moncifem/latticedb/issues/577).

- A revoked token never authenticates (the line is `revoked`); an expired one never does after its expiry.
- The gateway reloads the file at most 5 seconds after it changes (a stat of path, modification time and
  size each interval) and on SIGHUP. Restart-only is not acceptable for revocation.
- A reload that fails (permissions, parse) keeps the last good store and reports an error event (until the security event log of #530 exists, that report is a stderr line naming the file and the reason, never a token). If reloads
  keep failing for 10 minutes, token authentication is refused until a good file loads, so a typo in a
  revocation edit cannot keep the old token alive indefinitely.
- Every live connection records its account and token id. After each reload, and at a token's expiry,
  connections whose token is revoked, expired or gone are closed, within the reload interval plus one
  second. Revoking an account is revoking all its tokens.
- Rotation: issue a new token while the old one is active, move clients, then revoke the old one. The
  file grammar bounds the overlap to seven days and two tokens.

### What the HTTP and WebSocket layer must do

1. Read the token from the `Authorization: Bearer` header only. Never from a query string, a cookie, a
   path, a request body or a WebSocket subprotocol value; a request carrying `access_token` or similar in
   its URL is refused, and URLs are never logged with credentials (there are none to log).
2. Refuse a request with more than one `Authorization` header (the verifier takes one value and cannot see repeats; the host must).
3. Off loopback, require TLS (ADR 0021 applies to the gateway as to the pgwire listener). A token over
   plaintext on a non-loopback address is refused at start by configuration, not per request. On loopback
   plaintext is allowed for development, and the `LocalDevelopment` principal (ADR 0026) is never
   returned to an HTTP request without a valid token.
4. Answer every authentication failure with the same `401` and a `WWW-Authenticate: Bearer` header, and the
   same body, whether the header was absent, malformed, unknown, wrong, revoked or expired. Rate-limit by
   address before verifying.
5. Never log a header, token, secret, salt or verifier. `BearerToken`, `TokenEntry`, `CredentialStore`,
   `AuthError` and `StoreError` carry none in `Debug`, `Display` or error text (pinned by
   `token_never_appears_in_debug_display_or_logs`). Responses to the client never say which check failed.
6. Close the connection when its token is revoked or expires (above).

## Alternatives rejected

- **SCRAM over HTTP (RFC 7804).** Needs a multi-request exchange with server-side state and client
  support that MCP clients, HTTP libraries and the SDKs do not have. It proves a password to a server
  that then needs the verifier anyway; it buys nothing a high-entropy token does not.
- **Mutual TLS.** Strong, but the certificate lifecycle (issuing, installing, rotating, revoking) is
  heavier for an agent on a laptop than a header, and a TLS-terminating proxy hides the client certificate
  unless configured. It remains a possible later mechanism on top of the same principal.
- **Tokens in the query string.** They leak into access logs, proxy logs, browser history and `Referer`
  headers. Refused outright.
- **Signed stateless tokens (JWT).** Cannot be revoked before expiry without a server-side list, which is
  the credential file again, and add parsing surface and algorithm confusion.
- **A slow password hash for the verifier.** No benefit for 256-bit secrets and a per-request CPU cost an
  attacker controls.
- **Allowing people to choose tokens.** A short or guessable secret defeats every other control.

## Residual risks and what is not provided

- A bearer token is only as safe as its holder: anyone who copies it is the account. Off loopback it
  travels only under TLS, and the client must verify the certificate; a client that does not can be
  relayed (G-04 applies to tokens as to SCRAM). There is no channel binding ([#360](https://github.com/moncifem/latticedb/issues/360)).
- No per-token scopes, no rotation user interface (the credential tool, [#582](https://github.com/moncifem/latticedb/issues/582)),
  no OAuth (it depends on Phase 4 identity), no token introspection endpoint.
- A stolen file reveals which accounts have tokens and their salts, and allows no login: guessing a secret
  from a verifier is a 256-bit search.
- A root user or the account that runs `latticed` can read the file and change it. File ownership is not
  checked.
- Timing: constant-time comparison only (see above). Shape errors are faster than hash errors by design.
- The failure limiter fails open when its table is full, and clients behind one NAT share a budget.
- Between a revocation edit and the next reload (up to 5 seconds, longer if reloads fail) the token still
  works. That window is the price of not restarting.
- The gateway transport is `latticed::ws` ([#524](https://github.com/moncifem/latticedb/issues/524), part 1).
  Its TLS and connection bounds are [#578](https://github.com/moncifem/latticedb/issues/578) and are not
  done, so a token travels over plaintext on loopback only. Reload, revocation and expiry of live connections
  are implemented in #577 and tested over real sockets. Reloads are not an audit trail: the security event log
  (#530) does not exist yet.

## Consequences

- `lattice-api::bearer` holds the format, the verifier, the parser and the failure limiter, pure and
  sans-I/O. `latticed::load_credential_store` and `write_credential_store` do the file work.
- A fuzz target `bearer_verify` covers headers and credential files; a planted bug `TokenAcceptsPrefix`
  covers the comparison.
- Threat-model rows for B4 and gaps G-03 and G-05 are updated; the gate page records what was and was not
  run.
- The credential tool (`lattice account`, [#582](https://github.com/moncifem/latticedb/issues/582): creates tokens, revokes them by id or with their account, and sets the older token's expiry on `--rotate`), reload, revocation and
  the permission check per OS ([#577](https://github.com/moncifem/latticedb/issues/577)) and the endpoint
  ([#524](https://github.com/moncifem/latticedb/issues/524)) build on this file format.
- `latticed` now depends directly on `libc` (`=0.2.191`, default features off), only for the `O_NONBLOCK` and
  `O_NOFOLLOW` constants of the loader. It was already in `Cargo.lock` through other crates, so the lockfile
  gains one line and no crate arrives. No `unsafe` is added (`latticed` forbids it). `cargo deny check licenses
  bans sources` is clean; `libc` is MIT OR Apache-2.0 and has a build script that probes the compiler. It is
  not in the security-critical set of `docs/dependency-policy.md`.
