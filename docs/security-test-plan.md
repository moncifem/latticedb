# Security test plan

Companion to the [threat model](threat-model.md). The threat model lists boundaries, threats, mitigations and gaps (G-nn, E-n, P3-x). This plan turns each gap or risk area into a concrete test, fuzz target or verification item. It is a plan, not evidence: nothing here was run for this page, and "exists" means the file is on `main` at commit `adac101` (2026-10-29).

Items are owner-agnostic: whoever picks one up claims the issue first (see [agent-workflow.md](agent-workflow.md)).

## 1. Rules for security tests

These follow the project's existing conventions ([conventions.md](conventions.md), [agent-workflow.md](agent-workflow.md)) and apply to every item below.

1. A mitigation is not proven until the test fails with the mitigation removed. Add a planted bug (kernel and row code use `lattice-core`'s `planted-bugs` feature, [bugs.rs](../crates/lattice-core/src/bugs.rs)) or, for code outside the kernel, a documented mutant that the test kills. Proposed bug names are given per item.
2. Expected values are derived independently of the code under test: RFC vectors, a second implementation, a hand-written model. Never copy a value out of a run of the code under test.
3. Decoders and parsers stay strict and bounded and never panic on any input; every new decoder gets a fuzz target with seeds in `fuzz/seeds`.
4. Each fuzz target is in the nightly, weekly and 24 h matrices ([nightly.yml:58](../.github/workflows/nightly.yml#L58), [weekly.yml:19](../.github/workflows/weekly.yml#L19), [fuzz-24h.yml:15](../.github/workflows/fuzz-24h.yml#L15)), or the item says why not.
5. Test credentials and keys are generated by the test or read from fixtures. Never use a real key. Do not print credentials, nonces, proofs or cancel secrets in test output or logs.
6. Where a risk is accepted instead of fixed, write a characterization test that pins the boundary, so a later change that moves it is visible.
7. Machine load: quick targeted tests run locally (one crate, a named test, about a minute); volume runs, fuzzing, Miri, ASan, mutation and the full gate run on CI.

Priority: P1 before any release serves stored data over a network (or before the named component is reachable from a network); P2 before the owning phase's exit criteria are claimed; P3 when the area is touched.

## 4. Sequencing

1. Before the first storage-backed handler: S-01, S-02, S-15, then S-13. These are the P1 items and the ones that make a login mean something.
2. Alongside any change to authentication: S-03, S-04, S-05, S-06, S-12, R-2.
3. Before a sync transport ships: S-16, S-17, S-18, S-19, S-20, S-21, S-23.
4. Continuous and cheap: S-22, S-29, S-30, S-31, S-32, S-33, S-34.
5. Hardening when the area is touched: S-09, S-10, S-11, S-24 to S-28, S-35 to S-37.

## 5. What this plan does not cover

- Performance and capacity testing beyond the memory measurement in S-07.
- Physical access, a compromised host or compiler, and side channels beyond S-11 (threat model N-5, N-8).
- Social engineering of the maintainer.
- The static roadmap page in `web/`, `packs/` and `sidecars/` (not reviewed).
